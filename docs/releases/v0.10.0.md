# v0.10.0 — All-In-One Free SEO Tool

**Release date:** 2026-10-30
**Diff:** [v0.9.0 → v0.10.0](https://github.com/IamRamgarhia/All-In-One-Free-SEO-Tool/compare/v0.9.0...v0.10.0)

Most of the AI features were quietly failing, several numbers were quietly
wrong, and the WordPress plugin could not be downloaded at all. None of
these announced themselves — that is what this release is mostly about.

---

## 🤖 Most AI features were failing, and falling back silently

**Read this if the AI tools ever felt slow, or gave you a template when you
expected real writing.**

Running all five named AI features against a live key, four of them failed.
Not crashed — *degraded*. The executive summary returned its deterministic
template instead of AI. The content summariser and review drafter returned
"the AI provider did not respond". Sentiment returned nothing. Only the GEO
SWOT got through, and it took 33 seconds.

The models were fine. `gemini-flash-latest` — an **alias**, and the default
model — was answering `503 This model is currently overloaded` or hanging
past 45 seconds, while `gemini-2.5-flash` answered the same prompt in
**1.2 seconds**. The fallback chain existed for exactly this and never got
a turn: the per-attempt timeout let the first model spend the entire
budget, so a model that hung for 30 seconds consumed all of a 25-second
budget and the working model one line away was never tried.

Each attempt now gets a share of the remaining budget rather than all of
it. And the default is the pinned `gemini-2.5-flash`, not the alias — an
alias tracks whatever Flash currently *is*, so it can change underneath an
install with no release and no changelog. Pricing is identical.

| feature | before | after |
| --- | --- | --- |
| Executive summary | 25.0s → template | **9.7s → real AI** |
| Sentiment | 20.0s → nothing | **9.1s** |
| GEO SWOT | 32.8s | **18.7s** |
| Content summary | 30.0s → no answer | **12.4s** |
| Review reply | 30.0s → no answer | **11.3s** |

With the default model also fixed, those land at **1–4 seconds each**.

If you had explicitly chosen Gemini Flash (latest) in Settings, you keep
it — the change only moves what a new or unconfigured install picks.

## 📉 Numbers that were wrong, and said so with confidence

Every one of these produced a plausible figure. None threw an error.

**Traffic comparisons were inflated by about 7%.** Five places computed
"this period versus last" by splitting a list of days in half with
`rows.slice(half)` — which is one day *longer* than the other half on an
odd count. The GA4 fetch asks for 29 days, so a complete response is
always odd: the recent half always got 15 days against 14. On a 7-row
window it was 4 against 3, about +33%. One of those five is the figure
printed in your client's PDF report.

**The daily traffic-drop alert missed roughly half the drops it promised.**
Search Console date ranges are inclusive, so the "trailing 7 days" window
was 8 days and the prior one 7. A real 10% weekly drop came out as
**+2.9% growth**, and the alert only fired once a site had lost about 21%.

**A blocked rank check was recorded as "not ranking".** `checkRank` never
throws — a captcha comes back as a null position with an error attached,
and two callers read only the position. That wrote fake drops into keyword
history, and made the local-pack heatmap report "0% in pack" and draw every
cell as **lost** in red when Google had simply shown a captcha.

**Search Console averages were being subtracted from live scrapes.** Those
measure different things, so the difference is movement nobody made. It
drove ranking-drop notifications and the "stormy" SERP volatility label.

**Client snapshots recorded the site's best 200 queries as its totals.**
`organicClicks` is one of five metrics the anomaly detector runs a z-score
over, so the wrong number was also the noisy one. Average position was a
plain mean where Search Console weights by impressions.

**The canonical audit's "Critical" count.** `??` binds looser than `+`, so
2 broken + 5 multiple + 9 noindex displayed as **2**.

**The AI usage page** summed a 500-row slice and labelled it a total,
including the month-to-date figure shown beside the spend cap. Enforcement
was never affected — that sums in SQL — so it under-reported rather than
overspent.

## 🔌 The WordPress plugin is now a download

**Read this if you ever tried to install it.**

The instructions could not work. The README did not link it. The app and
the docs both told you to install `wordpress-plugin/seo-tool-bridge.php`
and then sent you to **Plugins → Add New → Upload** — a form that only
accepts a `.zip` and rejects a bare `.php`.

The zip that did exist was gitignored, so nobody outside the repository
ever saw it, and it had been built in September and never rebuilt: v0.6.0
inside, v0.6.1 in the source beside it.

**[Download the plugin](https://github.com/IamRamgarhia/All-In-One-Free-SEO-Tool/raw/main/wordpress-plugin/seo-tool-bridge.zip)** — 30 KB, separate
from the app download, and attached to this release. It unpacks into a
proper `seo-tool-bridge/` folder and leaves the 60 KB test harness out.

A test now compares the PHP inside the zip against the PHP beside it byte
for byte, because committing a binary is only safe with something holding
it to its source.

## 🔎 Rank checking no longer depends on a browser that keeps getting blocked

Measured from one machine with a plain HTTP request: Google returned a
JavaScript interstitial, DuckDuckGo a CAPTCHA, Bing an empty shell. The
fallback was blocked and the fallback's fallback was blocked.

The chain is now **Search Console → SearXNG → Brave → headless browser**,
with the browser last because it is the slowest and the most blocked.

- **SearXNG** — open-source metasearch you host yourself. Free, no key, no
  browser. It queries several engines and returns whatever answered.
- **Brave Search** — official API with a free tier. It searches Brave's own
  index, so its readings are kept as their own series and never subtracted
  from a Google number.
- **Attach to a Chrome you started** — run your own browser with
  `--remote-debugging-port`, and rank checks use your profile and session
  rather than a fresh headless one. Loopback only.

All three are optional and off by default:
**Settings → Advanced → Where rankings come from**. The panel opens by
telling you that for sites you own, Search Console beats all of them.

## 🖱️ The launcher, and the Update button that never worked

**Read this if you installed by downloading the zip.**

**A downloaded install could never update itself.** The Update button ran
an updater that only understands git checkouts; on a zip install it
refused — *"This install is not a git repository"* — and told you to
re-run a `curl | bash` one-liner from the README. That is not an
instruction for someone whose entire interface is a window with buttons
in it, which is exactly who the download is for. So the headline install
was a dead end from the day it shipped.

It now updates itself: it asks GitHub for the latest **release** (not
the tip of main), checks the version, downloads, validates the archive
*before* touching anything, and copies over your install without
deleting. Your database, `.env`, encryption key, backups and uploads are
never written. The launchers sitting above `_system/` get refreshed too,
so they cannot drift a year behind the app they start.

**Every control-panel button could refuse on a machine with Docker
installed.** Install Docker Desktop for anything at all, leave it not
running, and the panel could no longer tell which kind of install this
was — and it is built to refuse rather than guess, because guessing
starts a second app against an empty database. Correct, and it made the
panel useless. It now reads the evidence: a Docker install keeps its
database inside Docker, so a `data.db` in the folder means this is a
normal install. When nothing settles it, the panel asks, with two
buttons, instead of naming an environment variable.

**"Installed, not running" over a running app.** The panel trusted
`.seo-port`, which records where the launcher last *put* the app rather
than where it is. Measured here: the file said 3399 while the app
answered on 3000, so the panel reported it stopped and pointed "Open the
app" at a dead port. It now asks the app, and checks the answer belongs
to this install — port 3000 is the most contended port in local
development.

**Launching twice gave you a black window with an error.** It now opens
the browser at the panel that is already running, and steps to the next
port if something else holds 4321.

**Update takes a backup first.** An update runs migrations, and a SQLite
migration that adds a constraint rebuilds the table. There was a Back up
button and nothing that made you press it before the one action that
rewrites your schema.

## 💾 Backups moved out of the app folder

They were written beside `data.db` — inside the folder people delete,
move, replace or re-download, and which the new updater writes a release
over. Every copy of the database lived in the blast radius of the one
action most likely to destroy the original.

They now go to the folder your operating system designates for
application data:

| | |
| --- | --- |
| Windows | `%LOCALAPPDATA%\SEO Tool\Backups` |
| macOS | `~/Library/Application Support/SEO Tool/Backups` |
| Linux | `~/.local/share/seo-tool/Backups` (or `$XDG_DATA_HOME`) |
| Docker | unchanged — the mounted volume, the only place a backup survives the container being recreated |

Backups already beside your database are left alone and still appear in
the restore list. `SEO_BACKUP_DIR` overrides all of it.

**Not Documents**, which was the first choice and is where this project's
sibling GST app puts them. It was measured before shipping, and
`mkdir` inside `C:\Users\<you>\Documents` *hung* past a five-minute
timeout rather than failing — that folder is routinely redirected into
OneDrive or watched by sync and anti-virus filter drivers. Taking a
backup is synchronous, so a hanging folder does not make it slow, it
freezes the app with no error at all.

## 🧰 Smaller things you will notice

- **A help button on every tool.** 18 of the 92 had none at all, and the
  other 74 linked to a page of ninety rows rather than their own. Each now
  deep-links to its own entry in the reference.
- **`get_ai_usage` over MCP** — ask Claude what this install has spent,
  broken down by feature, provider, model and client. 29 tools now.
- **The MCP docs page** said "22 tools" long after there were 29, and only
  covered three clients. It is generated from the server's own list now,
  and covers Claude Code, Claude Desktop, Cursor, VS Code, Windsurf, Cline
  and Zed, with troubleshooting.
- **`docker compose up -d` never worked on a clean checkout.** The
  entrypoint correctly refuses to boot without `APP_PASSWORD`; the docs
  just never said so. Fixed in README and HOSTING.
- **The control panel's backup list** showed filenames. It now says what
  each backup *is* — "safety copy, taken before database update 0075" —
  and no longer renders a never-measured value as "0% in pack".
- **Tabs** on the per-client page and the knowledge hub, which were the two
  longest scrolls in the app.
- **GEO SWOT sends the page in 66ms** instead of waiting 23–31 seconds for
  the model; the analysis streams in behind it.
- **Six foreign keys added** to columns that could orphan rows, and the
  migration runner now survives a table rebuild instead of silently
  deleting child rows while reporting success.

## Upgrading

Nothing to do. Migrations run on start; this release adds one
(`0075_fk_client_cascades`), which cleans up orphaned rows before adding
the constraints and recreates the indexes a SQLite table rebuild drops.

If you use the AI features and never chose a model, you move from
`gemini-flash-latest` to `gemini-2.5-flash`. Same price, and currently the
difference between working and not.

Docker users: `docker compose up -d` needs `APP_PASSWORD` in a `.env`. It
always did — the documentation is what changed.
