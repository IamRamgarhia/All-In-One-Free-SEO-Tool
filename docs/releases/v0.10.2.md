# v0.10.2 — All-In-One Free SEO Tool

**Release date:** 2026-11-19
**Diff:** [v0.10.1 → v0.10.2](https://github.com/IamRamgarhia/All-In-One-Free-SEO-Tool/compare/v0.10.1...v0.10.2)

Two things this release is mostly about.

**You can install it without a terminal.** There is a Windows `.exe`
below, and a one-line command for macOS and Linux that downloads a
prebuilt app instead of compiling one. Neither existed before. Until
now the only install was `git clone` plus a build, which asked for
pnpm, a C++ toolchain and a working `main` — three things that fail for
reasons nothing to do with SEO.

**The agent finishes what it starts.** It used to apply a change and
stop. It now checks the live page afterwards, resolves the finding when
the change took, reverts it when it did not, closes the task, and
reports what happened to your traffic 28 days later. And when it
*can't* apply something, it writes the ticket for whoever can.

---

## 🖱️ A Windows installer, and a Mac/Linux one-liner

**Windows:** download `SEO-Tool-Setup-0.10.2.exe` below and run it. No
admin prompt — it installs for your user only, because asking for
administrator to install an SEO tool is a prompt you should decline.
It opens in its own window, not a browser tab.

**macOS / Linux:**

```bash
curl -fsSL https://raw.githubusercontent.com/IamRamgarhia/All-In-One-Free-SEO-Tool/main/install-prebuilt.sh | bash
```

That fetches a prebuilt payload — `node_modules` already installed,
`.next` already built — so there is no compile step and nothing to go
wrong that you can do anything about. It needs Node 20–26 and nothing
else.

`install.sh` still builds from source and is still the right choice if
you want unreleased code.

**What is honest about this:** every piece now compiles and the
filenames line up end to end, verified against the real build. **None
of it has been installed on a fresh machine yet.** A build that
compiles and a build that works are different claims. If the installer
fails for you, that is a bug worth reporting and not something you did
wrong — `installer/README.md` lists what has and has not been checked.

Three payloads are attached, one per platform **and per Node major**,
because the app contains compiled native modules that work against
exactly one Node ABI. The installer asks for its own and, if the
release has no match, lists what the release *does* carry and names the
Node version to install. It also re-checks the recorded ABI after
unpacking and before overwriting anything — a correctly-named archive
built on the wrong runtime is the one case a filename cannot catch.

## 🤖 The agent closes the loop

Before: the agent proposed a change, you approved it, it wrote it, and
that was the end. Whether the change worked was never checked, the
finding stayed open, and the task stayed on your list.

Now, after applying:

- it **re-reads the live page** and confirms the change is actually
  there,
- **resolves the audit finding** when it is, and **reverts** when it is
  not,
- **closes the task** that asked for it,
- and **measures the outcome** — clicks and impressions for that page
  28 days before and after, labelled `measured`, `thin` or `too early`
  so a number with four clicks behind it does not read like a result.

**"I fixed this — check it"** is the same verification without any of
the machinery. It needs no WordPress plugin, no API key and no Google
account: make the change yourself, press the button, and the tool looks
at the page and tells you whether it took. That is the only closing
path available to a Wix, Squarespace or custom-stack site, which is
most sites.

**Work is ranked by traffic, not severity.** A critical finding on a
page nobody visits used to outrank a medium one on your best-performing
page. Ranking now starts from the clicks each page actually gets, and
says `severity only` when there is no traffic data rather than
pretending the order means something.

**Findings the agent cannot fix become a developer ticket** — the
problem, the affected URLs, what to change and why, ready to send to
whoever owns the code. 30 of the crawler's 72 finding types can be
auto-fixed today; 25 are out of reach with a stated reason; 17 are real
gaps, and the file says which.

**Three changes, not a permanent grant.** Rather than asking for
standing permission, the agent offers a trial of three fixes so you can
see what it does before deciding.

## 🩺 It tells you when it has stopped working

A self-hosted tool that quietly stops working looks identical to one
with nothing to report. Settings → System health now checks eight
things and says so out loud: a WordPress connection whose plugin is
gone, a Search Console account with no properties, a fix queue that has
not moved, a client that has never been audited, nightly jobs that are
not running.

"We have not looked" and "nothing is wrong" never render the same.

**Nightly failures now say why.** Found by running the real sweep: on
the development install, 9 of 11 nightly failures were one client whose
domain had stopped resolving — and not one stored error said so. Three
separate bugs stacked up:

- A dead domain is `ENOTFOUND` through one code path and
  `net::ERR_NAME_NOT_RESOLVED` through the other, and both classifiers
  in the app knew only the first. A mistyped client URL therefore
  produced "Something went wrong" with a link to file a bug report.
- A failed request's error message is the bare string `fetch failed`;
  the code naming the cause lives one level down and was being thrown
  away before anything was stored.
- After fixing that, one check out of nine carried the real cause and
  eight did not, so a majority vote still reported "the reason was not
  recorded" **while holding the reason**.

It now reads: *"Every check that has to load a page failed: the address
does not resolve — the domain may be misspelled, expired, or a staging
site that no longer exists."* That is a one-minute fix that was
invisible for 67 days.

## 🧰 Ten finished tools nobody could reach

Ten tools were built, working and absent from every menu. They are in
the navigation now, and there is one tool registry instead of several
hand-maintained lists that had already drifted apart.

**Connections name what they unlock.** Settings used to imply a key did
more than it does. Each connection now lists the specific tools it
turns on, and how many of the tool set works with no key at all —
because "free" has to mean something you can check.

## 🔎 Rank checking, and the keyword list that was a third empty

A fresh install can now check ranks without any key: SearXNG ships in
the Docker compose file as an optional profile. Four sources in order —
Search Console, SearXNG, Brave, then a headless browser last, because
measured from a normal machine Google serves an interstitial and
DuckDuckGo serves a CAPTCHA.

A tracking redirect was also stealing a result position, reporting a
rank of 3 where there was none.

**A third of the keyword list had no data and nothing said so.** It
rendered as if the rank were simply unknown. It now says which rows
have never been checked, and why.

## ⚙️ Automations that report what happened

- The nightly sweep's result was being computed and thrown away. It is
  kept, so "27 of 38 checks ran — 11 could not" is now followed by
  *which* 11 and *why*.
- A run that half failed painted a green tick. It no longer does.

## 🔐 Security and scope

- Every critical and high advisory is cleared, and the pins are now
  where `npm` can see them as well as `pnpm` — these two files had
  already drifted, so a test asserts they agree in both directions.
- Google's October YMYL accuracy bar is applied to content checks.
- A Search Console property the connected account cannot actually read
  is caught and named, instead of failing silently every night.
- **The paid-ads tooling is gone.** This is a free-first SEO tool and
  ads were neither; `google-ads-api` is now an optional dependency that
  a normal install never fetches.
- The profile menu and the Guided/Pro switch were duplicated in the
  sidebar and the top bar, with two different wordings for the same
  control. One copy, in the top bar.

## Upgrading

**Nothing to do, and nothing to back up.** No database migrations in
this release — the schema is unchanged at 76 migrations. The WordPress
plugin is unchanged.

If you are on a downloaded zip install, press **Update**. If you cloned
the repository, `git pull` and restart.

If you installed by building from source and would rather not do that
again, the one-liner above will replace it with a prebuilt copy and
keep your database.

**Docker users:** `docker compose up -d` needs `APP_PASSWORD` in a
`.env` file. It always did; the documentation is what changed, in
v0.10.0.
