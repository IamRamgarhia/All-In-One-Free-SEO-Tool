# v0.10.3 — All-In-One Free SEO Tool

**Release date:** 2026-11-20
**Diff:** [v0.10.2 → v0.10.3](https://github.com/IamRamgarhia/All-In-One-Free-SEO-Tool/compare/v0.10.2...v0.10.3)

v0.10.2 was the first release anyone ever installed. This is what that
install found.

Every item below was discovered by one person double-clicking the
`.exe` and saying what happened. None of it was reachable from a test
suite, because every one of these passed CI.

---

## 🖱️ The installer

**It said WebView2 was missing on a computer that had it.** The
installer shipped only `SEO Tool.exe` from the host build.
`PublishSingleFile` bundles managed assemblies and the .NET runtime
into the exe but **not** native ones, so `WebView2Loader.dll` was left
behind. The P/Invoke threw `DllNotFoundException`, a blanket `catch`
turned that into "install WebView2", and the user already had WebView2
158.0.4370.26.

The two causes are distinguishable exceptions and now stay
distinguished: a missing runtime says go and install it, a missing file
of ours says **"This is a problem with the installer, not with your
computer — installing anything else will not fix it."**

**It said "Install" over a copy you already had.** Inno has no idea it
is upgrading. It now reads the installed version and says it is
updating from one version to another, that your clients, audits,
keywords and settings are kept, and the button reads **Update**.

**It could not close the running app.** `CloseApplications=yes` closes
an application by messaging its window — and the app is two processes,
the window plus a `node.exe` server that has none. Setup dead-ended on
"unable to automatically close all applications". The installer now
closes its own app with `taskkill /T` on the host, which takes the
server with it because the host is its parent.

**And it wears the app's mark**, generated from `public/icon-512.png`
at build time by a hand-written PNG decoder — `sharp` is not a direct
dependency and the `.ico` holds a single PNG-compressed frame, so
there was no decoder-free path.

## 🗄️ A first run had no database

The Docker entrypoint has always run `migrate.cjs && server.js`. The
Windows host ran `server.js` alone, so nothing created the schema.
Measured on a throwaway data directory: `/api/v1/health` answered 200
at 5.1s and the first real page returned **500**. Health is what hid
it — that endpoint does not touch the database.

**And the database was being written into the program folder.** Three
files resolve its path and they disagreed: `src/db/client.ts` and
`scripts/migrate.cjs` read `SEO_DB_PATH`, while `src/lib/data-dir.ts`
reads `SEO_DATA_DIR`. The host set only the second, so backups went to
`%LOCALAPPDATA%\SEO Tool` while `data.db` was created inside the
installed program folder — the one an update overwrites, and the
opposite of what the installer promised.

**Auto-backup ran every scheduler tick** as a consequence: it records
"when did I last run" in the settings table, inside the database it is
backing up. No schema, no write, so every tick read "never". Seven
copies of a 4 KB empty database in three minutes.

## 🖥️ The desktop app knew it was a browser

The host has set `SEO_LAUNCHED_BY=windows-host` since it was written
and **nothing had ever read it**. So inside the installed application
the app offered to *"Install as app (PWA)"* — a button that rendered
"Not available", because WebView2 has no install prompt — and to create
the Start Menu shortcut that had just launched it.

The same blindness made **Stop server** actively harmful there: it kills
the server that window depends on, then told you to "launch it again
from your desktop shortcut", which is a second copy of the app you are
looking at. It now says closing the window is how to quit.

## ⚡ Startup

Measured rather than guessed:

```
  259 ms  migrations
  896 ms  server accepting connections
 3432 ms  FIRST /api/v1/health   that one request took 2536 ms
 3449 ms  second health              17 ms
```

The server is up in under a second; the rest is Next's one-time runtime
and middleware init, paid by whichever request arrives first. Not
dependencies — the health route imports nothing at all and still pays
it.

It cannot be removed, only moved. The host now loads the first page
under the branded splash, so the wait looks like loading instead of
looking like nothing. WebView2 also initialises *while* the server
boots rather than after.

## 🤖 The agent was writing titles blind

`currentValue` was only ever populated for redirect findings. For a
title or meta description it stayed null — and `run.ts` builds the
drafting prompt's `pageTitle` from that field. So the model writing
your replacement title was told `Page title: (unknown)`.

On a real site that produced **"Active Dice Codes for Free Rewards"**
as a proposed home-page title for a digital agency: the model read the
brand as dice-game promo codes, which is a reasonable guess from a
domain name alone. It sat in the queue marked `risk: safe` for 68 days.

The planner now reads the live page once per URL before proposing, and
the approval preview distinguishes four states — the old value struck
through with its length, "nothing there yet", "couldn't read the live
page", and no row at all for kinds that never had one.

## 🔍 Smaller, and found the same way

- **A CDN was about to blame your fixes.** `recheckUrl` decides whether
  an applied fix is real by re-fetching the page — and fetched the
  plain URL, which a CDN answers from its own copy. On a cached site
  the fix works, the re-check sees yesterday's page, and the user is
  told their change did not take.
- **The home page could never be resolved.** WordPress's
  `url_to_postid()` returns 0 for a static front page, and neither
  fallback rescued it, so the most important page on any site was
  unreachable through the bridge.
- **The plugin's key field showed 43 of its 48 characters**, so a key
  copied by eye was always wrong, and the error said only that
  WordPress had rejected it.
- **The dot legend was in two places**, explaining a colour code on
  pages that have no dots.
- **The client page put the client third**, below a checklist and three
  advisory cards.

## Upgrading

Nothing to do. No database migrations in this release — the schema is
unchanged at 76. The WordPress plugin is **0.6.2**, up from 0.6.1; the
front-page fix needs it, so update it from Plugins → Add New → Upload.

If the installer cannot close a running copy it now says so and offers
to continue rather than dead-ending.
